# Техническое задание

_**Общие требования**_. Данное техническое задание формулирует следующие требования к вашему ПО:
1. Модуль, реализующий стек, должен быть выполнен как _статическая библиотека_. Это требование выполняется автоматически
([CMakeLists.txt](https://github.com/czertyaka/prosoft-c-stack/blob/master/CMakeLists.txt)) - весь код из `cstack.c` попадет в библиотеку.
2. Библиотека должна _собираться_, т.е. в ней не должно быть ошибок компиляции и линковки (за исключением ситуации отсутствия на машине
сборки стандартной библиотеки C).
3. Библиотека _не должна иметь зависимостей_ иных, чем стандартная библиотека C.
Не сомневаюсь, что при должном упорстве можно найти готовые реализации стека на С, удовлетворяющие нашим требованиям.
Это не наш случай :smiling_face_with_tear:.
5. Функции библиотеки должны удовлетворять требованиям, описанным ниже.
6. Библиотека должна корректно _освобождать ресурсы памяти_ при должном использовании.
7. Библиотека должна быть _отказоустойчива_ (в разумных пределах) _к входным данным_ функций, т.е. должны быть введены разумные проверки на нулевой указатель, нулевой размер и т.д. Понятно, что проверить валидность переданного указателя (например, что он не указывает в начало адресного пространства) невозможно или очень трудно, но полноценная проверка и не является ответственностью библиотеки.
8. В ходе нормального выполнения и использования кода библиотеки не должны возникать ошибки сегментации, переполнения стека, обращения к
памяти и др.
9. Библиотека не гарантирует: освобождение ресурсов памяти при некорректном использовании функций библиотеки; отсутствие недекларированного
поведения в случае передачи невалидного указателя (за исключением нулевого указателя).

Валидация этих требований будет осуществляется в процессе код-ревью, сборки, статического анализа и юнит-тестирования. Обратите внимание, что последние два
валидатора могут быть выполнены вами в целях экономии времени (в том числе и вашего). Но это лишь предложение по оптимизации процесса
проверки, а не требование. Обратите внимание, что юнит-тесты могут быть модифицированы в случае выявления недостаточности
проверок/несоответствия приведенным выше требованиям. Требования - первичны, а тесты всего лишь их выражают.

_**Особенности нашей реализации стека**_.
1. Библиотека может одновременно обслуживать несколько стеков.
2. Количество одновременно обслуживаемых стеков не должно быть меньше 10.
3. Данные, хранимые в стеке, не типизированны.

**_Требования к функциям библиотеки_**.
Одним из аргументов большинства функций библиотеки является _хэндлер_ стека с типом `t_hstack`. Этот тип является псевдонимом типа `int`
и к реализации стека в памяти отношения не имеет. Скорее это абстрактный идентификатор, который нужен, чтобы отличить один стек от другого.
Отмечу, что в C использование _хэндлера_, (_дескриптора_), является стандартной практикой. Примеры:
[hInstance](https://learn.microsoft.com/ru-ru/windows/win32/learnwin32/winmain--the-application-entry-point) в `WinAPI`, возвращаемое
значение функции [open](https://man7.org/linux/man-pages/man2/open.2.html) в `POSIX`. Объявление этого типа находится в заголовочном файле
[cstack.h](https://github.com/czertyaka/prosoft-c-stack/blob/master/cstack.h).

* `hstack_t stack_new(void)`  
**Описание**: Создать новый стек.  
**Возвращаемое значение**: `-1` в случае ошибки выполнения, хэндлер нового стека с неотрицательным значением в случае успеха.

* `void stack_free(const hstack_t stack)`  
**Описание**: Удалить стек, если соответствующий хэндлеру стек существует.  
**Параметры**: `stack` - хэндлер стека.

* `int stack_valid_handler(const hstack_t stack)`  
**Описание**: Проверить хэндлер.  
**Параметры**: `stack` - хэндлер стека.  
**Возвращаемое значение**: 0 - соответствующий хэндлеру стек существует, 1 - нет.

* `unsigned int stack_size(const hstack_t stack)`  
**Описание**: Получить количество элементов в стеке, если соответствующий хэндлеру стек существует.  
**Параметры**: `stack` - хэндлер стека.  
**Возвращаемое значение**: количество элементов в стеке, если соответствующий хэндлеру стек существует, или 0 в противном случае.

* `void stack_push(const hstack_t stack, const void* data_in, const unsigned int size)`  
**Описание**: Добавить элемент данных из буфера в стек, если соответствующий хэндлеру стек существует.  
**Параметры**: `stack` - хэндлер стека; `data_in` - указатель на буфер с данными; `size` - размер буфера с данными.

* `unsigned int stack_pop(const hstack_t stack, void* data_out, const unsigned int size)`  
**Описание**: Извлечь элемент из стека и записать данные этого элемента в буфер, если соответствующий хэндлеру стек существует
и размер выходного буфера достаточен для копирования в него элемента стека.  
**Параметры**: `stack` - хэндлер стека; `data_out` - указатель на буфер для записи данных; `size` - размер буфера.  
**Возвращаемое значение**: размер записанных данных в байтах, если соответствующий хэндлеру стек существует и размер выходного
буфера достаточен для копирования в него элемента стека, или 0 в противном случае.

**_Подсказки по реализации_**. Прежде чем давать задание вам, я самостоятельно реализовал стек, чтобы было проще декомпозировать задачу и
подумать, в каких местах стоит дать подсказки. Эта часть необязательна к прочтению, ограничений на реализацию я не ставлю (кроме приведенных
в требованиях).

На мой взгляд, две главные проблемы, которые вам предстоит решить - как хранить сами данные в стеке и как устанавливать соответствие между
хэндлером и стеком.

Первая проблема решалась бы тривиально, если бы мы релизовывали стек, хранящий типизированные данные.
Тогда мы бы на этапе компиляции знали размер одного элемента стека.
Например, если бы мы хранили `int`, размер элемента стека в простой реализации был бы равен `sizeof(int)`.
В этом случае можно было бы вовсе обойтись без динамической памяти.
Для случая неизвестного на этапе компиляции размера я выбрал вот такое решение:
```c
struct node
{
    const struct node* prev;
    unsigned int size;
    char data[0];
};

typedef struct node* stack_t;
```
Такой подход напоминает другую структуру данных [односвязный список](https://prog-cpp.ru/data-ols/).
Из общего у них наличие указателя на предыдущий элемент.
При добавлении нового элемента в стек удобно в рантайме посчитать количество данных элемента стека
(размер указателя на предыдущий элемент `prev` + размер поля `size` + размер самих данных), аллоцировать
эти данные и заполнить их.
Это не единственно верный вариант, возможны альтернативы.

Вторую проблему я решил следующим образом: завел глобальный динамический массив указателей на верхушки стека так,
чтобы дескриптор стека являлся одновременно и индексом в этом массиве.
Добавил несколько оптимизаций, но общая идея такая.
```c
struct stack_entry
{
    int reserved;
    stack_t stack;
};

typedef struct stack_entry stack_entry_t;

struct stack_entries_table
{
    unsigned int size;
    stack_entry_t* entries;
};

struct stack_entries_table g_table = {0u, NULL};
```

**_Работа с GitHub Actions_**

В репозитории настроен [GitHub Actions](https://docs.github.com/ru/actions) — сервис непрерывной
интеграции, который автоматически собирает проект и запускает к нему проверки.
Описание workflow находится в файле
[ci.yml](../.github/workflows/ci.yml).
При открытии и обновлении пулл-реквеста запускается workflow `Test`, который:

1. собирает проект: статическую библиотеку `cstack` и юнит-тест (опция `WITH_TEST=ON`);
2. выполняет статический анализ файла `cstack.c` утилитами
   [cppcheck](https://sourceforge.net/projects/cppcheck/) и
   [clang-tidy](https://clang.llvm.org/extra/clang-tidy/);
3. запускает юнит-тест.

Итог выполнения отображается значком (зеленая галочка или красный крестик) рядом с коммитом,
а также в блоке *Checks* под описанием пулл-реквеста. Нажмите на название workflow `Test` в этом
блоке, чтобы открыть результаты выполнения.

Полный лог выполнения можно посмотреть на вкладке `Actions` вашего форка: выберите нужный запуск
workflow `Test` и откройте лог job `build`. В логе последовательно видны все выполненные этапы
(сборка, статический анализ, тесты); если какой-то из них завершился ошибкой, рядом с его
названием будет красный крестик.

**_Просмотр предупреждений анализатора_**

Статические анализаторы находят в коде потенциальные ошибки и нарушения стиля, о которых они
предупреждают. Срабатывания `clang-tidy` прерывают выполнение workflow, поэтому их необходимо
устранить, а если срабатывание ложное — подавить (см. раздел
«Подавление ложных срабатываний статического анализатора» ниже).
Предупреждения `cppcheck` к прерыванию workflow не приводят, но их также следует просмотреть
и, насколько возможно, устранить. В логе workflow этапы анализаторов называются `Cppcheck` и
`Clang-tidy`; все предупреждения можно найти поиском по строке `warning`.

Формат вывода clang-tidy: `файл:строка:столбец: warning: <описание> [<имя проверки>]`, например:

```
cstack.c:8:12: warning: Use of memory after it is freed [clang-analyzer-unix.Malloc]
    8 |     return *ptr;
      |            ^~~~
cstack.c:5:5: note: Memory is released
    5 |     free(ptr);
    8 |     return *ptr;
```

В конце в квадратных скобках указано имя проверки, которая нашла проблему. Строки с `note` —
дополнительное пояснение к предупреждению. В workflow включены проверки следующих групп:

* `clang-analyzer-*` — встраиваемый статический анализатор clang: потенциальные ошибки
  (использование освобожденной памяти, обращение по нулевому указателю, неопределенное
  поведение и т.п.);
* `cert-*` — требования стандарта [CERT C](https://wiki.sei.cmu.edu/confluence/display/c)
  (безопасность кода на C);
* `portability-*` — конструкции языка с ограниченной переносимостью;
* `readability-*` — читаемость кода (длина идентификаторов, скобки, магические числа и т.п.).

Полный список доступных проверок clang-tidy описан
[здесь](https://clang.llvm.org/extra/clang-tidy/checks/list.html).

Анализатор можно запускать и локально, чтобы не ждать workflow. Для этого нужен каталог сборки
с файлом `compile_commands.json` (CMake генерирует его автоматически при конфигурировании
проекта генератором Make/Ninja, см. [инструкцию по сборке](./build.md)):

```sh
clang-tidy \
  -p build \
  --checks='-*,clang-analyzer-*,cert-*,portability-*,readability-*' \
  cstack.c
```

Для этого потребуется установить утилиту `clang-tidy`
(Debian/Ubuntu: `sudo apt install clang-tidy`; Fedora: `sudo dnf install clang-tools-extra`;
ArchLinux: `pacman -S clang`).

**_Подавление ложных срабатываний статического анализатора_**.

Иной раз анализатор ошибочно пометит корректный код (ложное срабатывание, false positive).
Если вы уверены, что срабатывание ложное, его можно подавить комментарием прямо в коде.

`clang-tidy` использует комментарии `NOLINT`:

* `// NOLINT` — подавить все срабатывания на текущей строке;
* `// NOLINT(readability-magic-numbers)` — подавить конкретный чекер на текущей строке;
* `// NOLINTNEXTLINE` / `// NOLINTNEXTLINE(readability-magic-numbers)` — то же самое, но для следующей
  строки (удобно, когда срабатывание относится к строке выше комментария);
* `// NOLINTBEGIN(readability-magic-numbers)` ... `// NOLINTEND(readability-magic-numbers)` —
  подавить срабатывания в пределах блока кода.

Пример:

```c
const unsigned int MAX_STACKS = 10u;  // NOLINT(readability-magic-numbers)
```

`cppcheck` подавляет срабатывания комментарием `// cppcheck-suppress <название проверки>`, например:

```c
int x = 42;  // cppcheck-suppress constVariable
```

Подавляйте только действительно ложные срабатывания, по возможности указывая имя чекера и краткое
объяснение причины. Избыточное подавление диагностик будет считаться замечанием в процессе ревью.
Полный синтаксис NOLINT описан
[в документации clang-tidy](https://clang.llvm.org/extra/clang-tidy.html#controlling-the-checks-configuration).
